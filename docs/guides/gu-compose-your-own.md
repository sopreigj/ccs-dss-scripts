# 组合动作与自建流程

> 这一篇回答"**我要干一连串活，该用什么、放哪**"。
> 它只讲**选择与放置**；决定好之后"怎么写成不会静默失败的 `.bat` / CI"见
> [`gu-pipelines-ci.md`](gu-pipelines-ci.md)。

## 1. 你站在这一层的上面

仓库里的所有代码都是**给你的工具**，不是给你住的房子：

```
        你（或你的 CI、你的 Agent）      ← 用户层：不在这个仓库里
   ┌──────────────┴───────────────┐
   │                              │
atomic/<分类>/…js            workflows/…js      ← 你的两个入口
   │                              │
   │                        orchestration/…js   ← 仓库内部实现
   └──────────┬───────────────────┘
              ▼
          session/…js                            ← 仓库内部实现
```

所以"我怎么用这个仓库"通常不是"再写一层"，而是**在这两个入口里选**，然后把你自己的组合脚本
放在**仓库外面**（第 4 节）。

## 2. 我想做什么 → 用什么

| 我想做的事 | 用什么 | 放哪 |
|---|---|---|
| **一个动作**：连一下、读一段内存、烧一次 | 一个 `atomic/` 脚本 | 命令行直接调 |
| 多个动作，彼此**互不依赖**（读 A、读 B、读 C） | 你写一个 `.bat` / CI 脚本，**顺序调多个 `atomic/`** | 仓库外；骨架抄 [`../../examples/pipeline_template.bat`](../../examples/pipeline_template.bat) |
| 多个动作，**必须在同一次会话里**（烧录→运行→读回、写→跑→回读、跑到断点） | 用**现成的 `workflows/`** | 不用你写 |
| 一个同会话流程，**现成工作流里没有** | 往仓库里加一对：`orchestration/<动作>.js` + `workflows/…` | 仓库内部，见 [`../dev/dev-adding-a-script.md`](../dev/dev-adding-a-script.md) |
| 给 Agent / 自动化平台用 | 让它们调本仓库的脚本 | 见第 6 节 |

**看不懂就记一句**："要连续动作 → `workflows/`；其余 → `atomic/`"（速查表见
[`../reference/ref-decision-tables.md`](../reference/ref-decision-tables.md)）。

## 3. 判定"能不能拆成多条命令"

判据只有一条：**这一步需不需要上一步在会话里留下的东西**。

会话里会**留下**：符号表、断点、观察点、当前停机位置、外设配置。
会话一结束，这些**全部销毁**，而且**没有"重新挂上"的接口**。

| 你的一串活 | 能拆吗 | 为什么 |
|---|---|---|
| 读内存 A → 读内存 B → 读寄存器 C | **能**。三个互不依赖的 `atomic/` 调用 | 每一步自己开会话都能得到答案 |
| 烧录 → 运行 → 停机 → 读变量 | **不能**。用 `workflows/ccs12_2_0_load_run_read.js` | "运行之后那一刻的值"属于那一次会话；拆开后第三步是**另一次**会话，读到的是**另一个时刻** |
| 写变量 → 运行 → 回读确认 | **不能**。用 `workflows/ccs12_2_0_load_write_run_read.js` | 同上，而且还要靠会话内的 `--settle` 时序 |
| 设断点 → 跑到断点 | **不能**。用 `workflows/ccs12_2_0_run_to_bp.js` | 断点是会话的子对象，拆开后第二步的会话里没有它 |

⚠️ **最坑的失败形状**：拆开写**不会报错**。每一步都会各自报告成功，只是**结果不是你想要的**
（比如读到旧值、或者断点没命中却一路跑下去）。所以"能拆吗"这个问题必须在**动手前**问，
不能靠"跑一遍没报错"来验证。

> **本栈还有一个特有的坑**：参数里出现 `=` 或空格会让运行器在解析阶段中止
> （连结果标记行都不会打印）。所以**组合脚本里给脚本传表达式时不能直接写在命令行上**——
> 必须走环境变量通道（`CCS_WRITE_EXPR` / `CCS_EVAL_EXPR` / `CCS_SYMBOLS`）。
> 细节见 [`gu-pipelines-ci.md`](gu-pipelines-ci.md) 与
> [`../reference/ref-decision-tables.md`](../reference/ref-decision-tables.md) 表 3。

## 4. 你自己那层放哪、叫什么

**放哪**，三种，按推荐顺序：

| 放法 | 适合 | 注意 |
|---|---|---|
| **仓库外**（独立目录 / 你项目的仓库） | 绝大多数情况。**推荐** | 你的流程里必然写死目标配置、固件、变量名——**这些值本来就不入库**，放进这个仓库只会多一个跑不起来的空壳 |
| 仓库内，但加进忽略清单 | 你就是想在这个仓库里迭代 | 改 `.gitignore`；并清楚别人 clone 之后拿到的是一堆缺参数的脚本 |
| 直接改写 `examples/` 里的示例 | 一次性试 | 那是示例，改坏了不容易发现；**建议复制出去再改** |

**叫什么**（避开重名是第一原则）：

| 你的层是什么 | 建议名字 |
|---|---|
| 用户级流水线 / CI 编排 | **`pipelines/`**（最推荐——仓库里已有"pipeline"的说法） |
| 一个 CI job 里的步骤序列 | `jobs/` |
| 按用户目标封装的场景（"烧录并运行"、"采集数据"） | `scenarios/` |
| 参数化的配方（不同固件、不同地址） | `recipes/` |
| 给 Agent / 平台用的适配层 | `tools/`、`adapters/`、`mcp_tools/` |
| 只负责找 CCS、调运行器、处理退出码 | `runner/`、`launchers/` |

> **不要叫 `orchestration/`。** 仓库里已经有这一层，它的含义是"**被入口装载并驱动的、与技术栈无关的流程实现**"
> （见 [`../dev/dev-orchestration-layer.md`](../dev/dev-orchestration-layer.md)），
> 不是"总调度器"。重名会让下一个人分不清你说的是哪一个。

## 5. 什么时候才需要动仓库内部

分水岭很清楚：

- **用现成的 `atomic/` + `workflows/` 能拼出来** → 写在仓库外，不要动仓库。
  （一个同会话流程，多个动作的顺序由你在你的脚本里决定，这不算改仓库。）
- **需要一个新的"同会话多步"流程**，而 9 个现成工作流都不合适 → 才往仓库里加一对：
  `orchestration/<动作>.js`（流程）+ `workflows/ccs12_2_0_<动作>.js`（接线）。
  完整步骤见 [`../dev/dev-adding-a-script.md`](../dev/dev-adding-a-script.md) 与
  [`../dev/dev-orchestration-layer.md`](../dev/dev-orchestration-layer.md)。
  注意 `orchestration/` 里的代码**必须留在 ES3 子集内**（那份共享代码要与另一套实现通用），
  见 [`../dev/dev-language-constraints.md`](../dev/dev-language-constraints.md)。

**别为了"看起来整齐"去加脚本**：先查受控词汇表（[`../reference/ref-terms.md`](../reference/ref-terms.md)）
和现有脚本的用法行——大多数"缺一个脚本"的情况其实是"该用哪个工作流"。

## 6. 这个项目是什么

它是一个**面向命令行的调试工具箱**，并且是**为自动化与 AI 助手设计的**：

- 每个脚本都会打印**唯一的一行结果标记**（`CCS12_2_0_RESULT=OK`，失败时 `=FAIL <原因>`），
  所以调用方不必读退出码就有可靠的判据；
- 每个脚本自带**用法行**，参数形状固定（位置参数顺序 + `--选项`），不需要先读实现；
- **多步流程已封装成单个命令**（`workflows/`），调用方不必自己拆步骤、也不必理解会话边界；
- 每个动作都能**单独运行、单独观察**；
- 仓库提供 [`skills/`](../../skills/) 下的索引说明，供 AI 助手快速定位该读哪一篇文档；
- **配置与工程相关的值全部外置**（配置文件），所以同一套脚本能直接用于不同项目。

也就是说：**你可以把它当成一组带明确契约的命令行工具**，用你自己的流水线、CI 或 Agent 去调
（怎么调见 [`gu-pipelines-ci.md`](gu-pipelines-ci.md)）。
