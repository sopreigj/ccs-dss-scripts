# 排障：按症状进门

**第一步永远是看输出里有没有这一行**：

```
CCS12_2_0_RESULT=OK        ← 成功
CCS12_2_0_RESULT=FAIL <原因> ← 失败，原因就在这一行里
```

**输出里一行标记都没有**，说明脚本根本没跑到能打印它的地方——最常见是参数里的 `=` 或空格
把 cmd 弄崩了（见第 5 条），或者共享库没找到（见第 7 条）。这不是脚本内部的失败。

---

## 1. 提示找不到 `dss.bat`

两个入口用不同的链去找 CCS 安装位置：

| 入口 | 找法 | 相关环境变量 |
|---|---|---|
| `.vbs` 启动器 | 环境变量 > 配置文件 > **报错** | `CCS12_2_0_ROOT` |
| `examples\*.bat` | 配置文件 > 继承来的 `CCS_ROOT` > **报错** | `CCS_ROOT`（不是上面那个） |

所以**设 `CCS12_2_0_ROOT` 对 `examples\*.bat` 没有任何作用**。两个入口都没有"命令行参数"这一级。
完整覆盖链见 [`../reference/ref-configuration.md`](../reference/ref-configuration.md)。

**怎么办**：把 `ccs_root` 写进配置文件；或给 `.vbs` 启动器设 `CCS12_2_0_ROOT`；
或给 `.bat` 设 `CCS_ROOT`。启动器找不到时会打印
`Cannot find dss.bat: <路径>` 并以 1 退出。

## 2. 连不上目标（`Error -151` 一类）

按这个顺序查（前两步不需要开 CCS）：

1. 板子上电了吗？仿真器插好了吗？设备管理器里能看到探针设备吗？
2. **配置里声明的仿真器型号与手上插的是同一个吗？** 这是最常见的原因，而且很反直觉：
   用 v2 的配置去连 v1 的探针**照样能连上**，因为型号是从配置文件读的，不是探测出来的。
   所以要拿配置文件与设备管理器**人工对账**，不能靠"连上了"下结论。
3. 上一次调试进程是不是没退干净、还占着探针？（关掉 GUI 与遗留进程再试。）
4. 该 `.ccxml` 是不是被别的工程覆盖过？散落多份同名配置文件是常见事故源。
5. 换芯片（不是同型号的另一块板）还可能遇到内存位宽、寄存器名、符号作用域的差异。

## 3. 变量读不出来：`identifier not found`

读符号名需要**会话里有符号表**。两条路：

- 先用 `loadProgram` 烧一次（符号表随程序进会话）；
- 或给表达式类脚本显式指定固件文件（`--symbols "<out>"`）。

注意 `--symbols` 的值必须是可用路径；给了**空值**会直接报用法错误，而不是"静默地不加载符号表"。

## 4. 单步 / step out 失败

- **源码级单步需要符号信息**；没有符号就退回汇编级单步。
- **目标必须先停机**。目标在运行时不单步，脚本会以明确原因失败。
- `--from <位置>` 是"先运行到这里再单步"；如果目标已经停在该位置，脚本当作已到达，不会空等。

## 5. 表达式 / 赋值被 cmd 拆参

**两种崩法**：

| 写法 | 现象 |
|---|---|
| 给参数加了引号、里面含空格或 `=` | `... was unexpected at this time`，退出码 255，**连标记行都没有**（Java 没起来） |
| 不加引号、里面含 `=` | 在 `=` 处被静默拆成两个参数，脚本报用法错误（位置参数过多） |

**怎么办**：走环境变量通道。

| 环境变量 | 用途 |
|---|---|
| `CCS_WRITE_EXPR` | 默认赋值表达式 |
| `CCS_EVAL_EXPR` | 默认求值表达式（`;` 分隔） |
| `CCS_SYMBOLS` | 符号表路径 |

## 6. 这些脚本能用在别的项目上吗

能。脚本不依赖任何特定固件，只依赖三样东西：CCS 安装位置、目标配置文件、固件文件。
换项目时改配置文件里的 7 个键即可，脚本一行都不用动。

## 7. 报 `session/session.js not found above ...` 或 `... did not load`

这两条消息都来自脚本开头的引导块，**都带失败标记**，也都以 1 退出：

| 消息 | 原因 |
|---|---|
| `... not found above <目录>` | 从当前目录一直向上都没找到共享库 ⇒ 你不在仓库里执行 |
| `... did not load: <路径>` | 文件在，但装载没成功（引导块最后的哨兵断言失败） |

**怎么办**：从仓库内启动（任意子目录都行），或用 `.vbs` 启动器（它会把工作目录钉到仓库根）。
共享库与同名 `.js` 必须同目录成对存在，所以不要把脚本单独复制出去。

## 8. 中文变乱码 / 解析错位

脚本本体按**平台字符集**读取源码文件。在中文 Windows 上那是 GBK，所以：

- `.js` / `.vbs` / `.bat` **一律 ASCII**，中文只写进 `.md`；
- 配置文件读取另有专门处理（它能正确读 UTF-8）。

这不是"显示问题"，非 ASCII 字节会被解错，甚至可能吞掉换行导致解析错位。

## 9. 双击 `.vbs` 没反应 / 卡住 / 取消了

- **完成提示是弹窗，在没有焦点、也没有人点的会话里会一直等**。自动化场景请设
  `CCS12_2_0_NONINTERACTIVE=1`。
- 对话框被**取消**时，启动器以 1 退出（取消等于什么都没做）。
- 失败原因只写在弹窗里，所以自动化请直接调 `.js`。

## 10. 启动器报找不到共享库 / 找不到同名 `.js`

- 启动器依赖 `session/config.vbs`，所以 `.js` 与 `.vbs` 都不能单独搬走；
- **启动器不会因为"同名 `.js` 不存在"而报错**：它只是把路径拼进命令行交出去，
  而底层对不存在的脚本路径**仍然返回 0**、输出里**没有标记行**。
  所以判据只有一个：**没有 `CCS12_2_0_RESULT=OK` 就是失败**。
- 移动/改名脚本时，`.js` 与 `.vbs` 必须同目录成对一起动。

## 11. stderr 里有 `SLF4J: Failed to load class ...`，是不是失败？

不是。这是底层运行时的日志噪音，出现在 stderr，与成败无关。**判据仍然只有标记行**。

## 12. 同一地址每次读到的值都不一样，有时还是 0

**这是预期行为**，不是板子或脚本坏了。

每条命令自成一个会话，读到的是**本会话开始之后**的活值。如果那个地址是固件在持续改写的变量，
两次读到不同值才是对的。

想要"跑完之后紧接着的那个现场"，用一条工作流把"跑"和"读"放进同一个会话，见
[`gu-inspect-state.md`](gu-inspect-state.md)。
