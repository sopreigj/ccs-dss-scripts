# 工作流层：入口接线与状态依赖

> `workflows/` 里每个文件都是**纯接线入口**：它不含业务逻辑，只把"共享 main + 驱动"接起来。
> 业务逻辑在 `orchestration/`（与栈无关）与 `session/orch_driver.js`（与栈相关）里。

## 1. 为什么这一层只有 `.js`，没有 `.vbs`

工作流的参数是"一次实验的配方"（运行多久、写什么、读什么），不适合做成弹框逐项问。
原子脚本有启动器是因为"连一下、读一下"这类动作很适合双击。

## 2. 一个入口长什么样

以最简单的那个为例，入口做四件事：

```
1. 装载共享库  → 断言库的哨兵
2. 装载驱动    → 断言驱动的哨兵
3. 装载共享 main
4. ORCH_MAIN(ORCH_DRIVER)
```

三段装载各有独立的失败出口，都打印失败标记行并以 1 退出。
这样"到底哪一段没装载成功"在输出里一眼能看出来，而不是笼统的"脚本失败"。

**入口里不要放**：参数解析、业务判断、调用引擎成员。这些全部在下面两层。

## 3. 九个工作流与它们的会话内状态依赖

"依赖的会话内状态"这一列是这个表最有用的部分：**它决定了这个脚本能不能被拆成多条命令**
（答案是不能——拆了状态就丢了）。

| 工作流 | 一句话 | 依赖的会话内状态 |
|---|---|---|
| `load_run` | 装载后让它一直跑（**离开时不停机**） | 会话本身；装载带来的符号表 |
| `load_run_read` | 装载 → 跑 N 毫秒 → 停机 → 读表达式 | 符号表、目标运行状态 |
| `load_write_run_read` | 装载 → 等一段 → 写 → 跑 → 回读 | 符号表、写入的值、目标运行状态 |
| `run_to_bp` | 设断点并运行到它 | 断点对象、符号表 |
| `step` | 单步 N 次 | 断点/单步位置、目标停机状态 |
| `bp_write_action` | 在断点上挂一个写动作 | 断点对象、表达式求值上下文 |
| `watch_write` | 硬件数据观察点：谁在改这个地址 | 观察点对象（硬件资源）、目标运行状态 |
| `sample_exprs` | 定间隔采样到 CSV | 符号表、采样起始时刻 |
| `pin_drive` | 驱动一个空闲引脚并恢复 | 外设寄存器配置 |

**共同硬约束**：路径必须绝对且必须存在；地址必须带 `0x`；成败只看结果标记行。

## 4. 为什么不能拆成多次调用

把它拆开写成多条命令**表面上**能跑通，每一步都会各自报告成功，但：

- 第一步设的断点，第二步看不见（会话结束就销毁）；
- 第一步装载带来的符号表，第三步没有；
- 中间那次连接还可能把目标状态改掉。

所以"多步"必须落在一个脚本里。这也是这一层的存在理由——不是风格偏好，是机制决定的。

## 5. 新增一个工作流的检查清单

1. 先确认它**不是**"动作顺序"以外的东西（否则应该放在驱动里）；
2. 在 `orchestration/` 写共享 main（规则见
   [`dev-orchestration-layer.md`](dev-orchestration-layer.md)）；
3. 在这里加入口，照第 2 节的四件事写；
4. 更新本文第 3 节的表、[`../reference/ref-scripts.md`](../reference/ref-scripts.md)、
   以及 `test/README.md` 的装置表（若该脚本进入装置）；
5. 跑 [`dev-verification.md`](dev-verification.md) 里的门禁。

## 6. 与另一套实现的差异

本层有 **9 个**工作流，另一套有 **8 个**：本层多一个"在断点上挂写动作"。
两边其余工作流的概念一一对应，但入口接线的细节不同（另一侧没有引导块）。
见 [`../reference/ref-stack-differences.md`](../reference/ref-stack-differences.md)。
