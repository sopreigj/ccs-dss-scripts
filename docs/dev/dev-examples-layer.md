# 示例层：判定原语与流水线模板

> `examples/` 下有 5 个 `.bat`。其中 3 个是场景示例，另外 2 个是**可复用的构件**：
> 一个判定原语、一个流水线模板。本文讲后两个的契约，以及三个示例的取舍。

## 1. 为什么需要"判定原语"

不同技术栈的"一步成功了没有"判法不同：本栈看**退出码**，另一套实现
看 stdout 上的结果标记行。如果流水线直接依赖其中一种，骨架就没法复用。

`examples/run_one_step.bat` 解决这件事：**它是判定翻译器，不是透传器**。

```bat
call examples\run_one_step.bat <脚本.js> [参数...]
```

| 输出 | 退出码 | 触发条件 |
|---|---|---|
| `STEP_VERDICT=OK <脚本名>` | 0 | 被包的那一步成功 |
| `STEP_VERDICT=FAIL <脚本名>` | 1 | 任何失败（含用法错误、脚本不存在） |

**"不是透传器"这条很重要**：它把被包脚本的结果**消费**成自己的判定，成功时只回打一行。
所以：

- 想拿被包脚本的原始输出 → 不要经它，直接调脚本；
- 想知道"成功还是失败"这一个信息 → 用它。

它还负责：

- 找运行器（`CCS_ROOT` 从配置文件或环境变量来，两者都没有就报失败）；
- 检查脚本路径是否存在（**必须自己检查**：不检查就会出现"这一步根本没跑却算成功"）；
- 把被包脚本的输出收进日志，失败时把末尾输出打出来。

## 2. 流水线模板

`examples/pipeline_template.bat` 是骨架，默认是**零步**：

- 步骤之间固定延时（用 `ping` 而不是 `timeout`：后者在标准输入被重定向时会跳过延时）；
- 每一步都经判定原语，一步失败就停（**fail-fast**）；
- 最后一行是整条流水线的判定：`PIPELINE_VERDICT=OK` / `PIPELINE_VERDICT=FAIL`。

用法是**复制它、保留骨架、换掉步骤列表**。真板回归用的
`test/phase_d_pipeline.bat` 就是一个填好的实例。

## 3. 三个场景示例

| 示例 | 演示什么 | 为什么这样写 |
|---|---|---|
| `load_and_run.bat` | 装载并让它跑起来 | 用**一个**工作流而不是两个原子脚本——分开跑等于"烧完就复位" |
| `load_set_run_read.bat` | 装载 → 写 → 跑 → 读回 | 演示 `--settle` 的必要性：写完立刻运行读到的是旧值 |
| `breakpoint_step.bat` | 断点、单步、观察点各一次 | 每一步都是一个独立工作流：这三件事的现场不可能跨调用保留 |

三个示例都把默认值从配置文件取（`EVAL_EXPR` / `WRITE_EXPR` / `WATCH_ADDR` / `SETTLE_MS`），
并在缺键时明确报错而不是猜。

## 4. 改这一层时

- **改判定原语的输出格式是破坏性变更**：所有引用它的流水线都要跟着改。改之前先改文档与模板。
- **场景示例不要"顺手"加功能**：它们的作用是"照着抄就能用"，复杂化会毁掉这个作用。
- 三个示例引用的脚本名、参数形状如果变了，**同笔更新**：
  本文、[`../reference/ref-scripts.md`](../reference/ref-scripts.md)、
  以及任何引用这些示例的文档。
- 判定原语的契约与另一套实现**一致（同名同契约）**，所以**改它要考虑那一侧**：
  见 [`../reference/ref-stack-differences.md`](../reference/ref-stack-differences.md)。
- **另一处差异**：那一侧的示例与模板里可能出现"参数走环境变量"的写法（因为那边的运行器
  会吃含 `=` 的参数）。本栈可以直接写在命令行上，**但两种写法在本栈都能用**——
  保持环境变量写法有助于两边骨架保持一致。
