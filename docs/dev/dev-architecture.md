# 架构：三层源码与它们的依赖方向

## 1. 全景

```
                      ┌──────────────────────────────┐
   用户调用       │ atomic/     一次调用做一件事    │  每个脚本自开会话
                      │ workflows/  一个会话内多步    │  只有 .js，没有 .vbs
                      └──────────────┬───────────────┘
                                     │ 装载（直接调用或经驱动）
                      ┌──────────────▼───────────────┐
                      │ orchestration/  共享 main     │  与技术栈无关，不含引导块
                      └──────────────┬───────────────┘
                                     │ 经驱动调用
                      ┌──────────────▼───────────────┐
                      │ session/   共享库             │  唯一知道本技术栈调用顺序的地方
                      └──────────────┬───────────────┘
                                     ▼
                                 调试引擎
```

**依赖方向是单向的**：`atomic/` 与 `workflows/` 依赖下面两层，`orchestration/` 依赖驱动，
驱动依赖 `session/`。没有任何一层反向依赖上层。

## 2. 每一层负责什么、不负责什么

| 层 | 负责 | 不负责 |
|---|---|---|
| `atomic/` | 参数解析、开一个会话、做一件事、给判定 | 跨步骤的流程编排 |
| `workflows/` | 在一个会话里串多步、把驱动接进来 | 具体怎么调底层接口（交给驱动） |
| `orchestration/` | 会话内的**动作顺序**与判定口径 | 任何与本技术栈绑定的调用形状；不含引导块 |
| `session/` | 参数校验、会话语义、结果标记、配置读取、驱动门面 | 具体业务动作（不决定"做什么"） |

判据：**动作的顺序**放在 `orchestration/`；**怎么完成一个动作**（具体调用）放在驱动里；
**文案与判定**由共享层统一。这样 `orchestration/` 里的代码可以原样给另一套实现用。

## 3. 会话就是状态的边界（整篇文档最重要的一条）

一次脚本执行 = 一个新会话。会话结束时：

- 符号表被释放；
- 断点、观察点被销毁；
- 单步位置、外设配置不保持；
- 会话结束时目标被释放，随后自由运行。

**没有"重新挂上"的接口**——引擎侧明确规定会话结束时它的所有子对象都被销毁。

由此推出三条设计规则：

1. **要连续的现场，就写成一个脚本**（这就是 `workflows/` 存在的全部理由）；
2. **任何跨脚本传状态的约定都是错的**，不是"不推荐"；
3. 参数与配置必须在**每次调用**里自足——所以配置文件与命令行参数是这个项目的两大输入面。

## 4. 停机规则（三重）

目标在脚本结束时应该处于什么状态，规则有三条，按出现顺序：

| # | 时机 | 行为 |
|---|---|---|
| 1 | 连接目标之后 | **显式停机一次**。因为"连接会不会复位/启动目标"在本技术栈没有明确文档，不假设 |
| 2 | 正常结束 | 默认**停机**再释放会话 |
| 3 | 被强行终止 | 注册的收尾钩子会**停机**（这是被终止时唯一能做的） |

**例外**：少数脚本的语义就是"让目标继续跑"（如"装载即运行"、"让目标运行"），
它们会在导致释放的那条路径之前**显式声明**"离开时不停机"。
失败路径仍然停机——`finishFail` 忽略这个声明。

## 5. 结果标记为什么打在 stdout 上

因为底层运行器的进程退出码不可靠（见
[`../reference/ref-api-dss.md`](../reference/ref-api-dss.md) 第 12 节）。
所以共享层把成败写成 stdout 上**恰好一行**的标记：

- `finishOk()`：**先**收尾（停机 + 释放会话），**再**打印 `CCS12_2_0_RESULT=OK`
  ——看到 OK 意味着"活干完了"，不是"刚开始"；
- `finishFail(原因)`：**先**打印 `CCS12_2_0_RESULT=FAIL <原因>`，再强制停机、释放会话、以 1 退出
  ——即使收尾阶段出问题，标记也已经出去了。

**原因只活在标记这一行里**，这是所有调用方与看日志的人唯一的解释来源。

## 6. 引导块：为什么每个脚本开头都有同一段代码

本技术栈的脚本语言**没有模块系统**：装载一个共享文件必须给绝对路径，而装载失败**不会抛异常**
（它只打印一行，然后照常往下执行）。这意味着"装载失败"会静默地变成"后面全部报错"。

所以每个脚本开头有一段**逐字相同**的引导块，做四件事：

1. 从当前目录向上找到共享库；
2. 确认文件存在；
3. 装载它；
4. **断言一个哨兵常量**，确认真的装进来了。

第 4 步是关键：它把"静默装载失败"变成响亮、带标记的失败。
`test/verify_static.ps1` 会机械复查这段块在全仓是**逐字节相同**的，
并给出可复算的摘要值——改它就是改全仓，装置会告诉你有没有改齐。

## 7. 目录与文件命名

| 目录 | 内容 | 命名 |
|---|---|---|
| `atomic/<分类>/` | 原子脚本 | `ccs12_2_0_<动作>.js` + 同名 `.vbs` |
| `workflows/` | 工作流 | `ccs12_2_0_<动作>.js`（无 `.vbs`） |
| `orchestration/` | 共享 main | `<动作>.js`（**不带版本前缀**，因为它与技术栈无关） |
| `session/` | 共享库 | 按职责命名 |
| `examples/` | 示例与模板 | 按演示的内容命名 |
| `test/` | 验证装置 | 按装置职责命名 |

前提是**每一步都能单独跑、且单独跑有意义**——这就是为什么工作流里没有 `.vbs` 启动器
（它们的参数是"一次实验"，不适合弹框）。
