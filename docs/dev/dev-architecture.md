# 架构：三层源码与它们的依赖方向

## 1. 全景

```
                      ┌──────────────────────────────┐
   用户调用       │ atomic/     一次调用做一件事    │  每个脚本自开会话
                      │ workflows/  一个会话内多步    │  只有 .js，没有 .vbs
                      └──────────────┬───────────────┘
                                     │ 引用（直接引用或经驱动）
                      ┌──────────────▼───────────────┐
                      │ orchestration/  共享 main     │  与技术栈无关
                      └──────────────┬───────────────┘
                                     │ 经驱动调用
                      ┌──────────────▼───────────────┐
                      │ session/   共享库             │  唯一知道本技术栈调用顺序的地方
                      └──────────────┬───────────────┘
                                     ▼
                                 调试引擎
```

**依赖方向是单向的**：`atomic/` 与 `workflows/` 依赖下面两层，`orchestration/` 依赖驱动，
驱动依赖 `session/`。没有任何一层反向依赖上层。

## 2. 每一层负责什么、不负责什么

| 层 | 负责 | 不负责 |
|---|---|---|
| `atomic/` | 参数解析、开一个会话、做一件事、给判定 | 跨步骤的流程编排 |
| `workflows/` | 在一个会话里串多步、把驱动接进来 | 具体怎么调底层接口（交给驱动） |
| `orchestration/` | 会话内的**动作顺序**与判定口径 | 任何与本技术栈绑定的调用形状 |
| `session/` | 参数校验、会话语义、配置读取、驱动门面 | 具体业务动作（不决定"做什么"） |

判据：**动作的顺序**放在 `orchestration/`；**怎么完成一个动作**（具体调用）放在驱动里；
**文案与判定**由共享层统一。这样 `orchestration/` 里的代码可以原样给另一套实现用。

## 3. 会话就是状态的边界（整篇文档最重要的一条）

一次脚本执行 = 一个新会话。会话结束时：

- 符号表被释放；
- 断点、观察点被销毁；
- 单步位置、外设配置不保持；
- 会话结束时目标被释放，随后自由运行。

由此推出三条设计规则：

1. **要连续的现场，就写成一个脚本**（这就是 `workflows/` 存在的全部理由）；
2. **任何跨脚本传状态的约定都是错的**，不是"不推荐"；
3. 参数与配置必须在**每次调用**里自足——所以配置文件与命令行参数是这个项目的两大输入面。

> **与另一套实现的差异**：那边有一个额外的机制细节——
> 会话结束时它的所有子对象被销毁，且**没有"重新挂上"的接口**（来自接口文档的明确说明）。
> 本栈同样按"不保持"设计，但证据来源不同（见
> [`../reference/ref-api-scripting.md`](../reference/ref-api-scripting.md) 的"已经实测确认的行为"与"仍未确证"两节）。
> 结论一致，依据不同——这一点在移植设计时值得注意。

## 4. 停机规则（三重）

目标在脚本结束时应该处于什么状态，规则有三条，按出现顺序：

| # | 时机 | 行为 |
|---|---|---|
| 1 | 连接目标之后 | **显式停机一次**。因为"连接会不会复位/启动目标"在本技术栈没有明确文档，不假设 |
| 2 | 正常结束 | 默认**停机**再释放会话 |
| 3 | 被强行终止 | 注册的收尾钩子会**停机**（这是被终止时唯一能做的） |

**例外**：少数脚本的语义就是"让目标继续跑"（如"装载即运行"、"让目标运行"），
它们会在导致释放的那条路径之前**显式声明**"离开时不停机"。
失败路径仍然停机——失败收尾忽略这个声明。

## 5. 失败怎么表达

本技术栈**有可靠的退出码**：运行器把脚本的退出状态透传出来。
所以约定是：

- 失败时以 **1** 退出，并把**原因写到输出里**；
- 成功时以 0 退出；
- 用法错误（参数形状不对）也走同一条路：报错 + 打印用法 + 以 1 退出。

> 这与另一套实现**相反**（那边退出码不可靠，只能看 stdout 标记行）。完整契约见
> [`dev-launcher-contract.md`](dev-launcher-contract.md)。

## 6. 没有引导块（与另一套的一个结构差异）

另一套实现的每个脚本开头有一段**逐字相同**的引导块，负责"找到并装载共享库、再断言装载成功"，
因为那里的装载失败不会抛异常。

**本栈没有这个东西**：脚本语言有正常的模块解析与异常机制，共享库由运行器与模块解析定位。
所以：

- 不要照搬那一边的引导块做法；
- 那边关于"引导块找不到库"的排障经验在本栈不适用；
- 本栈"找不到共享库"的表现是模块解析错误，见
  [`../guides/gu-troubleshooting.md`](../guides/gu-troubleshooting.md) 第 10 条。

## 7. 目录与文件命名

| 目录 | 内容 | 命名 |
|---|---|---|
| `atomic/<分类>/` | 原子脚本 | `ccs20_0_1_<动作>.js` + 同名 `.vbs` |
| `workflows/` | 工作流 | `ccs20_0_1_<动作>.js`（无 `.vbs`） |
| `orchestration/` | 共享 main | `<动作>.js`（**不带版本前缀**，因为它与技术栈无关） |
| `session/` | 共享库 | 按职责命名 |
| `examples/` | 示例与模板 | 按演示的内容命名 |
| `test/` | 验证装置 | 按装置职责命名 |
