# 踩坑账本

> 这里记的是"看起来对、跑起来不对"的事。每条都是：**现象 → 原因 → 判据 → 怎么避免**。
> 只写结论与判据，不写是谁在什么时候发现的。

## 1. 批量改名字，把已经是新名的文本又改了一遍

**现象**：全仓把旧前缀替换成新前缀之后，出现"新前缀套了两层"的东西
（例如版本串变成 `..._0_1_0_1...`），而且只在**原本就含新名**的位置出现。

**原因**：替换规则匹配的是短前缀，而有些文本里已经有"短前缀 + 版本后缀"的形式。
一次遍历里对同一段文本连续命中，就会把后缀当成前缀的一部分再补一次。

**判据**：替换后全仓搜"**替换结果套两层**"的形状（把新后缀重复一次当搜索词）。
命中数应为 0。

**怎么避免**：
- 用一次遍历的替换（不是对同一段文本反复替换），并让规则**排除已经带新后缀的位置**；
- 替换后再搜旧名字是否还有残留（两条搜索都要做：坏形状 + 残留）。

## 2. 同一份配置，两个入口读的是不同文件名

**现象**：配置文件明明在，脚本却报"没有配置"。只有**省略路径参数**的那种调用会报，
显式传路径的调用一切正常。

**原因**：改名时只改了一部分读取点。启动器与示例读的是新名字，而某处内嵌的解析器还在找旧名字。

**判据**：全仓搜配置文件名，**所有**读取点必须是同一个名字。

**怎么避免**：改名以后，专门跑一次"**省略参数的调用**"——因为显式传参的路径不会碰配置读取，
常规测试覆盖不到它。**这是最容易漏的一条。**

## 3. 管道把真实的退出码吃掉了

**现象**：命令明明失败，量到的退出码却是 0。

**原因**：把原生命令的输出接进 PowerShell 管道之后，`$LASTEXITCODE` 变成管道里最后一个
cmdlet 的退出码，不再是那个原生命令的。

**判据**：要看真实退出码，就在**不接管道**的情况下读，或者看脚本自己打印的结论。

**怎么避免**：判断成败时优先看脚本的输出；确实要看退出码时，别把它接进管道。

## 4. 在 PowerShell 里拼 `cmd /c`，引号被吃掉

**现象**：命令在 cmd 里跑得好好的，搬到 PowerShell 里就报"参数形状不对"或"位置参数过多"。

**原因**：PowerShell 会先解析一遍字符串，内部的引号可能已经不是你想给 cmd 的那个。

**判据**：同一串参数用 `cmd` 直接跑能通过、经 PowerShell 拼就不行——就是这个问题。

**怎么避免**：
- 直接用 `cmd` 执行 `.bat`（CI 里推荐）；
- 用 PowerShell 的调用运算符配合数组传参，而不是拼一个字符串；
- 把值放进环境变量（`CCS_EVAL_EXPR` / `CCS_WRITE_EXPR` / `CCS_SYMBOLS`）。

## 5. 直接调脚本，第一个参数被吃掉

**现象**：用 `node <脚本> <参数...>` 直接调用时，脚本把第二个参数当成了第一个。

**原因**：正常路径下运行器会在命令行里插入脚本名，所以脚本从第 3 个位置起读参数；
绕过运行器之后位置就错位了。

**判据**：参数"整体前移了一位"——就是这个原因。

**怎么避免**：脚本一律经运行器调用。

## 6. `.bat` 里漏写 `call`

**现象**：流水线第一步之后什么都没发生，而整条流水线的退出码仍然是 0。

**原因**：控制权被转移走了，后续步骤变成死代码，而退出码来自最后执行的那一步。

**判据**：**静态检查抓不到它**，只能靠审阅或真跑。

**怎么避免**：每个链式调用都写 `call`；改动这类文件后用真实调用验证一次。

## 7. 延时被跳过

**现象**：步骤之间的等待没有发生，导致目标还没准备好就被操作。

**原因**：用了 `timeout /t`，而它在标准输入被重定向（CI 里很常见）时直接报错并**跳过延时**。

**判据**：同上，静态检查抓不到。

**怎么避免**：用固定次数的 `ping` 作为延时。

## 8. "写进去了"和"值留住了"不是一回事

**现象**：赋值表达式报告成功，随后读回却是旧值。

**原因**：程序启动阶段的初始化把变量又赋了一遍，覆盖了刚写入的值。

**判据**：只有"写 + 让程序跑一段 + 回读"三步都做过，才能说"写入生效"。

**怎么避免**：用带"先等一段再写"的工作流，而不是先写再运行。

## 9. 相对输出路径会落到与调用者无关的地方

**现象**：导出文件明明成功了，但在当前目录与仓库里都找不到。

**原因**：相对输出路径由调试器一侧解析，落点与调用者的当前目录无关。

**判据**：找不到产物时，先怀疑它是相对路径。

**怎么避免**：输入与输出**都**用绝对路径。本项目在参数层强制这一点。

## 10. 改了共享层的代码，只改了一部分文件

**现象**：另一套实现侧或另一处同源代码出问题，或者机制自检报"两侧不一致"。

**原因**：`orchestration/` 与驱动的共享部分是**两套实现共用**的；
只在一边改了名字表或逻辑，另一边就立刻不一致。

**判据**：机械自检与键集 diff。

**怎么避免**：把共享层的改动当成"跨仓库改动"：先确认两侧都能接受，再动手；
改完两侧都要跑一遍自检。

## 11. 删掉一个脚本，却留下了引用

**现象**：读者按文档去找一个已经不存在的东西。

**原因**：删除只做了"删文件"，没有同步文档、示例、装置表与注释。

**判据**：删除后全仓搜索它的名字（含文档与注释），命中数应为 0。

**怎么避免**：把"删除"当成一个有清单的操作，见
[`dev-adding-a-script.md`](dev-adding-a-script.md) 第 4 节。
