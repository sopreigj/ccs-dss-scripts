# 本地验证：跑什么、按什么顺序

> 装置的**逐条判据**在 [`../../test/docs/dev-test-devices.md`](../../test/docs/dev-test-devices.md)。
> 本文只回答"**我刚改完东西，现在该跑什么**"。

## 1. 按改动范围选门禁

| 你改了什么 | 最低要求 | 需要真板 |
|---|---|---|
| 只改 `.md` | 静态检查（行尾与编码） | 无 |
| 改 `.js` 注释、改文档字符串 | 语法检查 | 无 |
| 改 `.vbs` | 语法检查 + **真跑一次该启动器** | 无 |
| 改参数解析或共享库 | 静态检查 + 参数层装置 | 无 |
| 改编排层或工作流 | 上面全部 + 编排层自检 + **真板跑一次相关工作流** | 部分 |
| 改退出码语义 | 全部 + **全仓搜索引用点** + 判定原语 | 视情况 |

## 2. 不需要真板的两套（提交前必跑）

```powershell
:: 语法、启动器编译、行尾、编码；编排层的机械自检也在这里
node test\static_checks.js

:: 参数层：声明、期望、行为三者一致（两个宿主各跑一次）
powershell -NoProfile -File test\verify_maxpos.ps1
pwsh       -NoProfile -File test\verify_maxpos.ps1
```

**为什么两个 PowerShell 宿主都要跑**：5.1 与 7 对原生命令的 stderr 处理不同。
只在一个宿主下"通过"**是缺陷**——一个只在单宿主成立的装置，本身就不合格。

## 3. 真板装置（有条件时跑）

| 装置 | 性质 |
|---|---|
| 退出码契约回归 | 需要真板（其中几项是纯参数层，可离线） |
| 实机审计（若干条拒绝路径与正常路径） | 需要真板，含**不碰硬件**的几条 |
| 驱动契约冒烟 | 需要真板：名字表里每一类至少真跑一次 |
| 已填好的三步管线 | 需要真板：端到端连一次 |

逐条判据见 [`../../test/docs/dev-test-devices.md`](../../test/docs/dev-test-devices.md)。
**跑完把新的读数写回对应文档**，否则下次没人知道它到底有没有跑过。

## 4. 怎么判断装置自己有没有坏

合格的装置必须**能红**。所以每个判决类装置都要带一个负对照（故意造一个坏样本，它必须报失败）。

**没有负对照的装置不算装置。** 加新装置时这条是硬要求，见
[`../../test/docs/dev-adding-a-device.md`](../../test/docs/dev-adding-a-device.md)。

> **与另一套实现的差异**：那一侧有一个"镜像 + 桩运行器"的装置，专门覆盖启动器的
> 无人值守分支，并带三条负对照与一个 `-SelfCheck` 开关。
> **本栈没有那个装置**——因为本栈的启动器不弹框、也没有无人值守开关，不存在那条路径。
> 这是两套装置清单之间最重要的差异，见
> [`../../docs/reference/ref-stack-differences.md`](../../docs/reference/ref-stack-differences.md)。

## 5. 改完后的自查顺序

1. 跑第 2 节的三条命令；
2. 改了启动器 → **真跑一次**；
3. 改了编排层 → 确认机械自检通过（静态检查已包含）；
4. 改了行为 → 用一次**真实调用**验证（真板或桩，取决于改动）；
5. 全仓搜一遍你改掉的旧名字/旧路径，确认没有遗漏的引用；
6. 同笔更新文档。
