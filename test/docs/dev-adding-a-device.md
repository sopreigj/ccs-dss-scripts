# 新增一个验证装置

**一个不能红的装置不算装置。** 本文是入库清单。

## 1. 先分清你要加的是哪一类

| 类别 | 特征 | 需要真板吗 |
|---|---|---|
| 静态检查 | 只读文件内容，机械可判 | 不需要 |
| 契约检查 | 通过桩/镜像跑代码路径，不碰真目标 | 不需要 |
| 真板回归 | 必须连上真实调试器 | 需要 |
| 一次性测量工具 | 回答一个具体问题，用完把结论写进文档 | 视情况 |

**优先后两类里"不需要真板"的那种**：能在公共 CI 上跑的装置才有价值。
需要真板的装置通常是"确认这条路径在本机上真的通"。

## 2. 硬性要求

1. **明确的期望输出**：装置必须自己打印一句可以判定的总结（通过 / 失败 / 计数）。
   看日志猜结论的装置不要入库。
2. **能失败的负对照**：判决类装置必须带一个"故意造坏"的用例，证明它**能红**。
   没有负对照的装置在别的仓库里已经被证明会反过来骗人。
3. **不依赖入库的夹具**：需要的输入在运行时生成（镜像、桩、临时文件），跑完删掉。
   一旦需要"入库的黄金文件"，这条装置就升级成了独立项目，要重新考虑结构。
4. **两个宿主下结论一致**：Windows PowerShell 5.1 与 7 都要跑过，并且给出相同判定。
   只在一个宿主下通过是缺陷。
5. **按自身位置推导仓库根**：不写死路径，从装置自己的位置向上推。这样它可以从任何位置跑。
6. **不碰真目标（除非它就是要碰）**：不需要真板的装置绝不能悄悄连上目标——
   那会让别人在没接板时无法复跑。

## 3. 入库步骤

1. 写装置，先确认它**在健康树上通过**；
2. 造一个坏用例，确认它**能报失败**（负对照）；
3. 把"需要什么、期望输出是什么"加进 [`../README.md`](../README.md) 的装置表；
4. 在 [`dev-test-devices.md`](dev-test-devices.md) 里补一节：查什么、判据、负对照、局限；
5. 如果是启动器相关的装置，还要同步它的分类表与启动器头部的声明；
6. 跑一次 [`dev-verification.md`](dev-verification.md) 里的全套，确认没有把别的装置弄红。

## 4. 写"局限"一节

每一节都要写清**这个装置查不了什么**。例：

- 静态门禁不启动任何会话，所以对目标行为一个字都没说；
- 启动器装置只覆盖非交互路径，不碰真实调试器；
- 真板冒烟证明的是"调用能跑通"，不证明业务语义正确。

**不写局限的装置，会被人当成"全都验证过了"。**
