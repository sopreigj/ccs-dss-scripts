# 装置清单与判据

> 本文逐个说明装置**查什么、判据是什么、有什么局限**。改完东西该跑哪些见
> [`dev-verification.md`](dev-verification.md)；新装置要满足什么见
> [`dev-adding-a-device.md`](dev-adding-a-device.md)。

## 分组

| 组 | 装置 | 需要真板 |
|---|---|---|
| **静态** | `verify_static.ps1` | 无 |
| **参数层** | `verify_launchers.ps1`（旧尝试）、`usage.ps1` | 无 |
| **启动器非交互路径** | `drive_checks.ps1` + `checks.ps1` + `policy_probe.vbs` | 无 |
| **真板** | `driver_smoke.js`、`phase_d_pipeline.bat` | **是** |
| **一次性测量工具** | `probe_*.js` | 视情况 |

---

## 1. `verify_static.ps1` —— 静态全套

**查什么**（每项都会打印一行实测计数，不靠断言推断）：

| 项 | 判据 |
|---|---|
| 语法 | 全部 `.js` 都能通过语法检查 |
| 引导块 | 全仓入口脚本的引导块**逐字节一致**，只有一种字节序列；若摘要与预期不符则失败 |
| 编码 | 代码文件里非 ASCII 字节数为 0 |
| 行尾 | 该 LF 的不含 CRLF；该 CRLF 的不含裸 LF（与 `.gitattributes` 对齐） |
| 启动器编译 | 每个 `.vbs` 都能被真正编译（注入一条立即退出的语句，只编译不执行） |
| 启动器负对照 | 故意改坏一个 `.vbs`，编译必须失败——证明这一项**能红** |
| 文档链接 | 所有 `.md` 里的相对链接按**文件所在目录**解析，必须存在 |

**局限**：

- 它不启动任何调试会话，所以对**目标行为一个字都没说**；
- 它检查不出批处理的两个坑（漏 `call`、误用 `timeout`）——那两个只有真跑才暴露；
- 引导块摘要会因为块内**任何字节**变化而变。块被有意修改后，需要用它的**重新标定开关**
  （`-Calibrate`）重新推导摘要，并把新值写回脚本。

**两个宿主都要跑**：5.1 与 7 对原生命令的 stderr 处理不同，只跑一个可能漏掉差异。

## 2. `usage.ps1` —— 启动器参数速览（只读）

打印每个启动器的位置参数顺序、存在性守卫、提示顺序。**不做判决**，给人读。

**用途**：给启动器的"给全参数"那一列（在启动器装置的分类表里）生成正确输入。
**加参数时先看它**，不要照抄旧表。

## 3. `verify_launchers.ps1` —— 对话框路径的旧尝试（保留，但不是关口）

**它想做什么**：自动应答启动器的输入框（选中已有文本 → 输入新值 → 回车），
然后断言"输入的内容真的进了命令行"。

**实测状态：本环境跑不通。** 几个用例全部失败，两种表现：一部分是启动器没被应答就一直等
（超时），一部分是系统直接拒绝注入按键。与脚本逻辑无关——注入手段在这个会话环境里不可用。

**结论**：

- 它会制造**假阴性**，所以**不作为验收关口**；
- 保留它是为了留下"试过自动化对话框"这件事与那条正确的判据；
- 非交互路径现在由第 4 节的装置接管，不再依赖任何人点击；
- 它抢焦点，跑的时候不要动键鼠。

## 4. `drive_checks.ps1` + `checks.ps1` + `policy_probe.vbs` —— 启动器非交互路径

**这是本目录存在的核心理由**：启动器的无人值守分支是"没有人点击、也没有测试能直接跑到"的那条路。

**怎么做到不需要真板**：

1. 把仓库**镜像**到系统临时目录；
2. 在镜像里放一个**桩运行器**（它不回真目标，只打印成功标记行，并把收到的命令行写进一个文件）；
3. 把相关的环境变量指向镜像；
4. 让每个启动器在无人值守模式下跑到它的参数处理与拒绝/放行分支。

于是"启动器这一层"被完整覆盖，而没有任何真实的调试会话被启动。

**四类判决**：

| 格 | 输入 | 判据 |
|---|---|---|
| 静态 | 启动器源码 | 提示辅助函数恰好一处、只出现一个输入框且在辅助函数内、**类别声明与头部说明自洽**、无裸 LF / BOM / 非 ASCII |
| 放行 | 只读启动器 + 不给参数 | 回显每一处提示、**每个默认值都真的进了命令行**、桩被调用、以 0 退出、无拒绝文案 |
| 拒绝 | 改状态启动器 + 不给参数 | 有拒绝文案、**一行回显都没有**、桩**没有被调用**、以 1 退出 |
| 显式 | 任一类 + 参数给全 | 无回显、无拒绝、**每个参数都进了命令行**、桩被调用、以 0 退出 |

**关键判据是"桩自己留下的文件"，不是回显**：启动器成功时不回显运行器的输出，
所以靠"某行文字出现在 stdout"判断会得到全格假失败。

**分类表的单一出处**是驱动脚本顶部那张表，与每个启动器头部的声明**双向核对**。

**负对照（`-SelfCheck`，三条）**：

1. 把默认类别翻转 → 政策单元必须失败；
2. 拿掉一个只读启动器的只读声明 → 放行格必须失败；
3. 给一个改状态启动器加上只读声明 → 拒绝格必须失败。

**局限**：它证明的是**启动器这一层**（哪条路径弹框、哪条路径拒绝、哪些值被拼进命令行）。
真实调试器的行为、真机的任何东西都不在它的覆盖范围内。

## 5. `driver_smoke.js` —— 驱动契约真板冒烟

**查什么**：驱动名字表里**每一类名字**至少被真实执行一次（参数层、会话层、重量级复合操作、
收尾）。每一步打印一行 `OK <名字>`，任何一步出错就以失败标记行收尾。

**需要**：真板 + 一个可用的配置文件。观察点那一步需要一个"固件持续写"的地址，
省略时从配置文件的 `watch_addr` 取。

**判据**：输出里出现"通过"字样且以成功标记行收尾。

**局限**：它证明的是"名字表里的调用在本技术栈上真的能跑"，不证明业务语义正确。

## 6. `phase_d_pipeline.bat` —— 三步真板管线

**是什么**：把流水线模板的步骤列表填好（检查连接 → 装载并运行 → 装载运行读回一个表达式），
它是**可复跑的回归资产**，不是给用户抄的骨架（那个角色属于 `examples/pipeline_template.bat`）。

**判据**：每一步都打印 `STEP_VERDICT=OK`，最后一行 `PIPELINE_VERDICT=OK`，以 0 退出。

**失败路**：把最后一步的表达式换成一个不存在的符号 → 求值失败 → `STEP_VERDICT=FAIL`、
`PIPELINE_VERDICT=FAIL`，以 1 退出。**这条失败路本身就是"判定翻译真的在工作"的证据。**

## 7. `probe_*.js` —— 一次性测量工具

**它们不是关口。** 每个探针回答一个具体问题，用完就把结论写进
[`../../docs/reference/ref-api-dss.md`](../../docs/reference/ref-api-dss.md) 的"未确证"表。

| 探针 | 回答什么 |
|---|---|
| 断点会话探针 | 断点是否跨会话存活 |
| flash 作用域探针 | flash 属性是会话内还是全局 |
| 复位类型探针 | 目标支持哪些复位类型 |
| 启动方式探针 | 不同启动方式的落点是否相同 |
| 字地址探针 | 内存寻址是按字还是按字节 |

保留它们的理由：**结论会过时**（换芯片、换工具版本），届时可以重跑，
而不是从零再写一遍测量代码。
